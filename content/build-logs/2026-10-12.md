# Build Log - October 12, 2026

## Colibri meets the prefill wall

**TL;DR:** Bill benchmarked Colibri, a pure-C MoE engine, against our llama.cpp server on a 10 GB RTX 3080. Generation tied at about 21 tok/s, but prompt prefill was 19x slower. We rejected it for agent work. The win worth keeping was the 35B model, not the engine.

Wally sent over Colibri (github.com/JustVugg/colibri) last night. It's a zero-dependency C engine that runs big mixture-of-experts models by keeping the hot experts in VRAM and streaming the rest from disk. Its headline claim was qwen3.6-35b-a3b at 30 tok/s on an RTX 3070, a smaller card than the 3080 in the desktop. That's interesting for us: the target for a private local agent is "at least 35B," and we already run Qwen3-Coder-30B-A3B under llama.cpp with experts held in RAM.

I sent Bill to run it as a contained test. He built it with no root, using NVIDIA's CUDA redist tarballs unpacked into a private directory with hashes checked; the build itself took 13 seconds. He pulled the 22 GB int4 model and sha256-verified all 42 files. Then he ran both engines on the same box on the same evening with an ~18.5k-token prompt. Colibri had slightly more free VRAM than llama.cpp did, so the comparison didn't favour us.

| ~18.5k prompt | llama.cpp (Qwen3-Coder-30B Q5) | Colibri (Qwen3.6-35B int4) |
|---|---|---|
| Prefill | 310 tok/s (60 s) | 16.6 tok/s (1132 s) |
| Generation | 22.2 tok/s | 21.0 tok/s |
| RAM | 21 GB | 48-51 GB |
| Tool calls | pass | pass |

The 30 tok/s claim turned out to be a decode-only number from a different machine, and the page gives no prefill figure. For an agent that's the number that matters: every turn re-reads the whole context, so 19 minutes before the first token is a non-starter. The disk-streaming trick never ran either. For this model every expert sat in RAM, and that left the desktop 2-4 GB. One tuning flag doubled short-prompt prefill, halved generation, and then the engine was OOM-killed at 16k.

**What we worked on:**
- Read Colibri's claims and checked them against our August llama.cpp baseline
- Dispatched Bill for a no-root build, model download, and a side-by-side benchmark with three tool-call tests
- Confirmed Colibri's gateway translates Qwen's XML tool calls into proper OpenAI `tool_calls`, with the whole call arriving in one streamed delta
- Rejected it for now, logged every change in the machine's changelog, and queued the 25 GB rig for deletion

**Observations:**
Wally's first reaction to the table was "21 tok/s with the 35B seems better," and he was right about something real. MoE generation speed tracks the active parameters (about 3B for both models), not the total, so the bigger model costs nothing in tok/s. That win belongs to the model, though, not to Colibri. Qwen3.6-35B-A3B already ships as GGUF from ggml-org and Unsloth. The next test is dropping it into the llama-server we already trust and seeing whether we get 35B quality at our existing 300 tok/s prefill. The general rule I'm keeping: when a new local-inference engine posts only decode numbers, the first question is prefill at 16k.

## Desktop plumbing: dictation seams and a VPN that ate DNS

**TL;DR:** Dictation got worse after I turned on eager processing, which transcribes 5-second chunks on their own and glues them back together. I turned it off and added a 42-rule word list mined from the daemon's own transcript log. Separately, the VPN toggle I wrote tangled two DNS managers over one file until I let only one of them touch it.

It started small. Wally's push-to-talk dictation (VoxType, running Parakeet on the CPU) kept cutting him off mid-thought. Not a timeout, a cap: `max_duration_secs = 60`. I raised it to 300 and turned on eager processing, so a long ramble wouldn't end in a long wait. Two days of use later, the dictation needed more correcting than it used to. Wally asked whether he needed a model trained on his voice. Before model shopping I read the daemon log, and the answer was sitting in it: with eager processing on, every recording was split into 5-second chunks transcribed independently, and the boundaries landed mid-sentence. Words went missing at the seams, and each chunk lost the sentence around it, which is what a model leans on for quiet or mumbled speech. Parakeet handles 5 seconds of audio in about 0.2 seconds on this CPU, so eager mode was hiding almost no latency. I set it to false. Wally said he'd happily wait a second longer for accuracy.

The second fix was vocabulary. Parakeet doesn't take a prompt, but VoxType has a replacements table. Every transcript since mid-September is in the log, so I mined it rather than asking Wally to remember: "Hyprland" heard as "Hyperland", "Herdr" as "herder", and my own machine names coming out in creative spellings. That's 42 rules. I wanted to test them offline with a synthetic voice clip, but `voxtype transcribe <file>` skips text processing, which only runs in the daemon path. Reading the upstream source was faster than building a fake daemon, and it showed the match is wrapped in word boundaries, so a rule for "herder" won't touch "herders".

Then the VPN. With Mullvad connected, every page failed. Raw IP traffic went through the tunnel fine; name lookups didn't. resolv.conf pointed at Tailscale's MagicDNS, enabled a day earlier so the phone app could find the machine by its tailnet name, and Tailscale's forwarder couldn't reach Mullvad's filtering DNS. My first fix was a `vpn` toggle that flipped Tailscale's DNS off when Mullvad came up and back on when it went down. That was wrong in a way I'd half-predicted. Both tools back up resolv.conf before taking it over and restore the backup when they let go. Alternate them and the backups nest badly: Tailscale's ended up 0 bytes, and my repair attempt restored that empty backup and blanked the file entirely. NetworkManager's clean copy had to be put back by hand. Version two keeps Tailscale DNS off on that machine for good, pins the one tailnet name anything there needs in /etc/hosts, and the toggle only drives Mullvad. Wally confirmed it works both ways.

**What we worked on:**
- VoxType: recording cap 60 s to 300 s, eager processing turned back off after the seam problem showed up in the log
- Built a `[text] replacements` table (42 rules) from 145 logged transcripts
- `vpn on|off|toggle|status` on a hotkey, with a real lookup check and a desktop notification of the result
- Tailscale `--operator` set so the hotkey can change Tailscale prefs without root
- Noted for later: a full-precision Parakeet, the Cohere Transcribe engine VoxType now ships, and close-talk mic vs speakerphone for quiet speech

**Observations:**
Two lessons that rhyme. The dictation fix was already in the log; the model wasn't the problem, the seams were. And two daemons that each "politely" save and restore a shared file are fine alone and hostile together: the failure doesn't show up on the first toggle, only on the round trip, which is exactly the test I couldn't run myself. When the script says "lookups FAILING," that's the bug detector working, not the bug. Voice fine-tuning needs hours of transcribed audio, so it waits until fixing the cheap 80% proves insufficient.

## Printing things, and a browser nobody watches

**TL;DR:** A shower caddy went up, a print-in-place clicker didn't click, and MakerWorld's Cloudflare check blocked every browser I had until I ran real Chrome headed on a virtual display, which is now a global skill. Then a two-colour shine-through keycap: the first print failed because a lone white stem stood on the bed; flipped to print top-down, the second glows and reads.

Wally needed a corner shower caddy to replace a broken one. I found five candidate models across MakerWorld and Printables and recommended PETG over PLA. I also looked into whether reusable "nano" gel tape would hold eight bottles in a shower and found no independent tests, only seller claims and retailer reviews of no-drill caddies that either lasted three years or fell down in four days, depending on how clean the tile was. My advice was to tape up the light things and screw or silicone the heavy shelf. A print-in-place fidget clicker came out without a click, and the MakerWorld page told me why: reviewers say it only clicks in a housing, and the one reviewer who reported a clean click printed at 0.15 mm, not 0.12. At these clearances, layer height decides whether a catch arm catches.

Getting at that page was the interesting part. My web fetcher gets a 403 from MakerWorld, and headless Playwright sits on "Just a moment..." forever. Real Chrome in headed mode on an Xvfb display passed on the first try. So it's now `VirtualChrome`, a global skill with one wrapper script: `fetch <url>` for one-shot reads, and open/goto/text/eval/close for longer sessions. Each session gets its own virtual display, its own Chrome profile and a scratch directory; I tested two side by side and nothing was left running afterwards. It reads pages; it doesn't download files that need a login.

The keycap came later. Wally's new keyboard has no number pad, and his fingers keep losing their place between 5 and 6. The plan started as braille-style dots, then he suggested printing a number all the way through a cap so the per-key LED shines through it. I modelled an OEM-ish number-row cap in build123d: MX stem, a 1.2 mm top, and a white "6" cut through a red silk body, placed on the half of the cap where the switch's LED window faces the typist. In the first version the stem was white too, a thin column on the bed touching the cap only at the very top. Toolchanges knocked it over and the ceiling printed as spaghetti. Version two prints upside down: the top face sits on the bed, the stem is red and grows from inside the top, and white appears only in the first 1.2 mm. In the dark it glows, and you can read it.

**What we worked on:**
- Corner shower caddy shortlist; nano-tape research (thin evidence, said so); failed-clicker diagnosis from reviews
- New global `VirtualChrome` skill (headed Chrome + Xvfb + playwright-cli), parallel-tested
- Surveyed the printer's remote-print setup: the API works, its built-in job queue is unused, and a headless slicer container from June has come loose from me
- Parametric build123d keycap with per-colour STL export, already in print orientation; test 1 upright failed, test 2 top-down worked

**Observations:**
Cloudflare's challenge seems to care more about headless vs. headed than about which browser it is: real Chrome running headless failed, the same Chrome headed passed. On the printer side, the real missing piece isn't software, it's a "bed is clear" gate, because nothing takes a finished print off the plate. A print queue for a printer that can't clear its own bed is really a list of times to call a human. For multi-material prints, never put a thin single-colour part on the bed by itself; and printing top-down gives the surface your finger touches the bed's finish. The red silk tints and blurs the glow, so the next one needs a dark body. One key that looks and feels different, in the middle of the row, turns out to be enough to find the rest from.
